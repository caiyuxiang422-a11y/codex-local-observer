# ADR 0003：用户定义里程碑与本地进度存储

状态：已采用（2026-08-26）

## 问题和边界

项目完成度不能由 token、对话轮数、代码行数、提交次数或文件修改数代替。第三步只记录用户定义的里程碑，并把用户明确填写的权重和百分比转换成可复核的派生指标。健康度也不能凭“看起来差不多”自动宣称完成。

本阶段不保存 Prompt、推理内容、源代码正文、命令输出、凭据或远程数据。

## 已知事实和假设

- Tauri 可以为应用提供平台相关的 `app_data_dir`；它不属于项目工作目录，适合保存本地应用状态。
- 当前 UI 尚未需要历史事件查询、复杂筛选或多进程并发写入，因此一个有版本号的 JSON 文档足以承载 MVP。
- 用户输入的里程碑是主观计划，不是外部验收证据；后端只能验证格式和执行确定的算术。

## 数据契约

`save_project_progress` 接收一个规范化项目路径和完整的里程碑列表。每项必须有唯一 `id`、标题、1–1000 的权重、0–100 的 `progressPercent`，以及 `planned`、`inProgress`、`done` 或 `blocked` 状态。状态与百分比必须一致：planned 为 0，inProgress 为 1–99，done 为 100，blocked 小于 100。列表最多 100 项。

`get_project_progress` 和保存命令都返回带 `schemaVersion`、`source`、`updatedAt` 和 `confidence` 的快照。完成度和健康度各自携带证据；没有里程碑时完成度为 `unknown`，不是 0%。

## 派生规则

完成度是纯函数：

```text
Σ(weight × progressPercent) / Σ(weight)
```

结果四舍五入到整数百分比。即使结果为 100%，状态仍为 `derived`，证据会明确说明它不等于外部验收或发布完成。

当前健康信号只使用用户里程碑：没有里程碑为 `unknown`；有任一 blocked 为 `blocked`；全部达到 100% 且无 blocked 为 `healthy`；其余为 `attention`。这些状态的 `source` 和 evidence 会明确说明 Git、测试、构建和验收输入尚未纳入。后续可把第二步的 Git/test/build 快照作为额外证据接入，但不能把单一脏 Git 状态直接判为失败。

因此第三步的“健康度”在当前版本是“里程碑健康信号”，不是完整项目质量评分。界面必须同时保留第二步的 Git、测试和构建卡片，并明确展示两者的来源边界；不能用里程碑 100% 覆盖已知的测试/构建失败。

实现上，Rust 快照保留上述里程碑健康信号；前端在已有第二步快照明确显示测试/构建失败或超时时，将展示层信号降为 `blocked`，在检查未执行或未配置时将手工 `healthy` 标为 `attention`。这只是带证据的展示合并，不会改写后端保存的用户数据，也不会把 Git 脏状态单独判为失败。

## 存储和安全

- 文件名为 `project-progress-v1.json`，位于 Tauri `app_data_dir`；不会写入项目目录。
- 文件有 2 MiB、200 个项目和每项目 100 个里程碑的上限；读取后再次校验，拒绝未知版本、重复路径和非法里程碑。
- 保存流程在同目录创建唯一临时文件，写入、`sync_all` 后用同文件系统替换；失败时清理临时文件并保留旧文件。
- 进程内保存操作串行化。跨多个应用实例的并发写入尚未解决，出现该需求时应升级到 SQLite 或文件锁。

## 取舍和回退

JSON 是可读、易备份、无新依赖且可删除回退的 MVP，但不适合高频事件、历史查询、迁移链和多进程并发。届时迁移到 SQLite，并保留 schema version 和导出格式；不能把“删文件重建”当作正常升级路径。
