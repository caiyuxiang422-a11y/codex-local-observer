# ADR 0002：第二步加入项目状态

状态：已采用（2026-08-26）

## 问题和范围

第一步只能看到由观察台启动的 Codex 任务事件。第二步需要在同一页面补充四类项目状态：

- 当前 Git 分支；
- 未提交文件数量及基本分类；
- 测试结果；
- 构建结果。

截图只定义了展示目标，没有定义“测试结果”和“构建结果”是否应该自动执行。自动执行项目脚本可能联网、写入缓存或执行项目作者提供的任意脚本，因此本阶段采用用户显式触发的检查，不在应用启动或后台轮询时偷偷运行。

## 已知事实和假设

- Git 状态可以通过本机 `git` 命令在指定项目目录读取，不需要读取 Codex 私有文件。
- 测试和构建通常由项目的 `package.json` 脚本定义，但并非所有项目都使用 Node，也不一定存在 `test` / `build` 脚本。
- 项目目录必须由用户提供，并且在 Git 工作树内；不能默认扫描整台磁盘。
- 当前应用以 Tauri Rust 后端执行本地命令，React 只消费统一快照。

## 方案

新增项目状态适配器和一个版本化的 `ProjectStatusSnapshot`：

1. `get_project_status` 在固定、规范化的项目目录中读取 Git 分支和 porcelain 状态；不把路径拼接成 shell 字符串。
2. 测试/构建只接受 `all`、`git`、`test`、`build` 四种固定检查类型。后端读取 `package.json` 的脚本和 lockfile，选择对应包管理器并执行 `run test` 或 `run build`；前端不能传入任意程序和参数。
3. 检查输出只保留限长、脱敏的尾部诊断，不保存到数据库；结果包含退出码、耗时、更新时间、来源和置信度。
4. 检查有超时和输出上限。无脚本、找不到包管理器、非 Git 目录、超时和非零退出分别显示为可解释状态，而不是伪造“通过”。
5. 项目状态与 Codex 任务事件分离；任务完成后可以刷新 Git 快照，但不把事件数量或 token 数量当作项目完成度。

## 取舍、成本和风险

- 运行项目脚本不是纯只读操作：测试/构建可能生成缓存、修改文件、访问网络或执行任意仓库脚本。因此只提供显式按钮，并在 UI 标明这一点；默认不自动运行。
- Node 包管理器和脚本约定并不覆盖所有语言项目。没有可识别脚本时显示“未配置”，后续可以增加 Cargo/Python 等适配器，但不能把一个语言的命令硬套到所有项目。
- Git porcelain 输出需要按机器格式解析，不能依赖本地化文本或简单按空格切分；路径列表有数量上限，避免大型仓库造成内存和界面压力。
- 结果是某一时刻的本地快照，不是持续一致性保证。用户在检查后修改文件时，结果会变旧，界面必须显示更新时间并允许刷新。

## 回退方案

如果项目没有 Git、脚本或包管理器，仍保留第一步任务监控；项目状态卡片显示“不可用/未配置”，不会阻止只读 Codex 任务启动（但任务本身仍要求 Git 工作树）。

## 验收

- Git clean、staged、unstaged、untracked、重命名、删除、detached HEAD 和非仓库 fixture；路径含空格及 shell 元字符不得改变命令语义。
- 有效、失败、超时、缺少脚本和缺少包管理器的测试/构建检查。
- 测试输出截断和常见密钥脱敏；前端不显示浏览器预览中的伪造结果。
- `npm run check`、Rust `cargo fmt --check`、`cargo test` 和 `cargo clippy --all-targets -- -D warnings` 实际运行并报告结果。
